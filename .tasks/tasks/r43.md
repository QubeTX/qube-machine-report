## Why

The corrected v4.3.0 product candidate passed its original local and hosted PR
gates, but release review identified privileged-installer, credential-custody,
and publication-provenance controls that must be repaired before the candidate
can become a full release. The operator explicitly authorized the complete
repair, merge, publication, release, and deployment campaign.

## Scope

In scope: release-chain and privileged-installer hardening; independent review
and security scanning; Apple and crates.io credential cutovers; reconciliation
of hardened `main` into PR #14; exact-main CI and crates publication; the
immutable failed v4.3.0 and v4.3.1 tags plus one v4.3.2 fix-forward tag; private draft
assembly; native Windows and macOS acceptance; public-byte audit; post-public
updater/Linux/macOS smokes; homepage deployment; and release ledger closure.

AMD64 Linux laptop, Raspberry Pi, and other physical gates remain independent.
Authorization never substitutes for evidence, and unavailable physical proof
must remain open rather than inferred.

## Plan

1. Land the release-chain hardening through protected PR #15.
2. Complete Apple environment-only and crates.io OIDC-only cutovers, including
   legacy credential and temporary bootstrap removal.
3. Reconcile hardened `main` into PR #14 and repeat exact-head local, hosted,
   security, performance, and reachable-hardware qualification.
4. Merge the accepted exact SHA so the main push starts CI and the registry-uncredentialed
   crates waiter; publish through OIDC only after it proves that exact CI run.
5. Preserve failed immutable `v4.3.0` and `v4.3.1`; create only `v4.3.2` after
   its exact-main CI/OIDC and native Apple Bash-3.2 staging proof, and keep the
   GitHub Release private through the exact
   24-to-30-to-validated-to-34 asset chain, and publish only from the macOS
   finalizer after Windows and native Apple acceptance.
6. Audit immutable public bytes and complete post-public smokes before deploying
   the homepage and closing the release ledger.
